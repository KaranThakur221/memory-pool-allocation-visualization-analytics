## 2026-10-24 — Durable experiment history

**Feature/component:** Experiment persistence and retrieval  
**Original issue/requirement:** The specification requires experiment configurations, workloads, operation logs, metrics, final state, and benchmark results to survive backend restarts. Inspection confirmed `g_experiments` existed only in process memory and the README documented history loss on restart. SQLite development headers and Valgrind are unavailable in this environment, so adding a system database dependency would not be portable here.  
**Files created/modified:** Added `src/experiment_store.h` and `src/experiment_store.cpp`; registered the module in `CMakeLists.txt`; integrated loading and append-before-publish behavior in `src/api_server.cpp`; added a full-record persistence round-trip test in `tests/allocator_tests.cpp`.  
**Changes implemented:** Added a versioned append-only local history store. It serializes each `ExperimentRecord` including operation sequence, metrics, benchmark results, final memory JSON, and errors. Startup loads saved records; malformed/truncated storage causes a clear startup failure rather than silently discarding history. Workload requests report a persistence error instead of claiming a saved experiment when the append fails. The storage path is configurable with `MEMORY_POOL_EXPERIMENTS_PATH`, defaulting to `data/experiments.bin`.  
**Bugs discovered/fixes applied:** Durable history was missing. Added explicit persistence and error handling; the saved detail API now loads its records from the same restored history set.  
**Tests executed/results:** CMake build of `allocator_tests` and `memory_pool_server` succeeded. CTest passed 1/1. Persistence test round-trips strings with quotes/newlines, operation records, metrics, benchmark fields, final memory JSON, and errors. Frontend `npm test` passed 4/4; `npm run build` succeeded. A live HTTP test created a fixed-size workload record, stopped and restarted the backend using the same isolated file, then verified history and detail retrieval retained the record, two operations, strategy, 37-byte request, 64-byte consumption, and workload metrics.  
**Build status:** Successful for both updated C++ targets.  
**Remaining limitations:** Persistence is a versioned local append-only file rather than SQLite; it is intended for one server process and does not include multi-process locking or explicit fsync guarantees. Corrupt/truncated records are reported and prevent startup; automatic repair is not implemented.  
**Current audit status:** In progress; other specification areas still require verification.

## 2026-10-24 — Allocator semantics, benchmarking, and live UI state

**Feature/component:** Allocator behavior, benchmark accuracy, pool configuration, frontend state integrity  
**Original issue/requirement:** The specification requires distinct First-Fit/Best-Fit behavior, fixed-size accounting, safe invalid pointers, actual benchmark timing and utilization metrics, configurable pool settings, and no fabricated frontend memory state.  
**Files modified:** `src/memory_pool.cpp`, `src/api_server.cpp`, `src/benchmark.h`, `src/benchmark.cpp`, `tests/allocator_tests.cpp`, `frontend/src/App.jsx`, `frontend/src/styles.css`, `frontend/src/experimentDashboard.js`, `frontend/test/experimentDashboard.test.js`.  
**Changes implemented:** Fixed-size allocations now consume the configured block while preserving the user-requested size, and reject requests larger than the block. Added fixed-size regression coverage. Replaced undefined relational comparisons on unrelated pointers in deallocation with checked integer-address range validation. Added deterministic 3,000-operation allocator invariants and an observable First-Fit versus Best-Fit selection test. Benchmarks now report measured whole-workload duration separately from allocator call timings, use peak and final utilization separately, record deallocation outcomes, and measure fixed-size internal fragmentation using requested bytes. Pool initialization API and UI controls now accept bounded capacity and strategy/mode configuration. The frontend no longer renders a hardcoded empty-pool state when the backend is unavailable; it displays loading/error state until valid C++ state is received. Memory block widths now follow their actual proportions without minimum-width distortion.  
**Bugs discovered/fixes applied:** Benchmark `execution_time_ms` had been populated with average allocation latency, peak utilization was indistinguishable from final utilization, fixed-size requests larger than their block could be reported successful after allocating only one block, and foreign-pool pointer comparisons used undefined relational comparisons. Addressed these defects and added regressions.  
**Tests executed/results:** C++ build succeeded; CTest passed 1/1, including deterministic allocator invariants, strategy distinction, fixed-block requested/consumed accounting, benchmark timing/utilization, and persistence round-trip. Frontend `npm test` passed 5/5; Vite production build succeeded. Live HTTP validation of the new pool configuration and benchmark persistence remains pending.  
**Build status:** C++ targets and frontend production bundle built successfully.  
**Remaining limitations:** Step/pause/resume workload controls, random workload generation integrated with backend execution, robust CSV validation, and the requested AI-agent management/dashboard are not yet implemented or verified. Benchmark experiment logging is being integrated and still requires live API testing.  
**Current audit status:** In progress; no claim that every specification criterion is met.
